# Editorial intake workflow

This is the repeatable weekly workflow for adding Zeauddin Ahmed archive records. The public Cloudflare Sites deployment must only receive records that pass the validation and review gates below. The workflow is intentionally review-first: it can identify duplicates and missing evidence without changing the public archive.

## 1. Create an intake record

- Create a stable `work_id` (for example, `2026-09-19-brics-sangbad`).
- Save the original title exactly as it appears in the source.
- Record publication name, issue/edition, date, page number, and original URL when available.
- Store the source location and discovery method in the private editorial workspace.
- Record the article text location, image plan, and whether a preservation PDF is possible.

Use the template generated by:

```powershell
node scripts/weekly-article-intake.mjs template path\to\new-intake.json
```

The intake file is a staging record; it is not automatically published.

## 2. Run the intake check and deduplicate

- Run `node scripts/weekly-article-intake.mjs check path\to\new-intake.json`.
- Treat an exact title match, exact title/date match, or normalized original-URL match as a duplicate candidate. Resolve the candidate before importing anything.
- The check compares the intake against both the 24 curated records and the folder-imported archive records. It never invents a URL or silently overwrites an existing record.
- Compare the title, byline, publication, and date against the source.
- Mark date confidence (`exact`, `approximate`, or `unknown`).
- Keep a short evidence note explaining what was checked.
- Do not infer missing facts from search snippets or secondary mentions.

## 3. Review rights and source evidence

Choose one explicit status before publication:

- `full_text_permitted` — permission or a clear public-domain basis is recorded.
- `excerpt_only` — title, metadata, approved excerpt, and source link may be shown.
- `metadata_only` — only bibliographic metadata and the original source link may be shown.
- `hold` — do not publish until the rights question is resolved.

The full article may be added to the public archive only when `rightsStatus` is `full_text_permitted` and the evidence note records the permission basis. If the original URL is missing, leave `originalUrl` empty and add the item to the URL-review queue; do not manufacture a link.

## 4. Prepare the standard image

- Create one mature, topic-specific archival ink-and-collage illustration from the article’s main theme.
- Keep it elegant and uncluttered; do not add irrelevant objects, invented newspaper branding, or source-page advertisements.
- Save the approved local asset under `public/articles/` and record `heroImage`, `heroCaption`, `imageCredit`, and `imageSourceUrl`/provenance in the intake record.
- A generated archive illustration is acceptable when it is explicitly credited as archive-created; a real external image must have a verifiable license/source.

## 5. Editorial review

- Check Bengali spelling, punctuation, names, dates, and links.
- Confirm that OCR corrections are documented and that scans remain distinguishable from transcriptions.
- Check that no private personal data has entered the public record.
- Add the reviewer and review date to the audit trail.

## 6. Decide whether a preservation PDF can be made

The validator prints `PDF: READY` only when the record has a non-empty original URL, publication identity, publication date, complete source text, a source reference/snapshot path, and `full_text_permitted` rights. Otherwise it prints `PDF: SKIP` with the missing evidence. A skipped PDF is recorded for later investigation; it is not replaced with a speculative reconstruction.

When ready, generate the source-faithful PDF in the designated folder:

`G:\My Drive\05 Reference Library\Articles\Zeauddin Ahmed's Columns`

Use a descriptive filename such as `2026-09-19 - BRICS Summit and Bangladesh Diplomatic Calculus - Sangbad.pdf`. Do not include a retrieval date unless explicitly requested.

## 7. Import, build, and publish

Only records marked `verified` and with a rights status other than `hold` may be exported into the public archive. The export should include a source link and a visible rights note where the full text is not available.

1. Resolve all duplicate candidates and validation errors.
2. Import the reviewed record with the existing folder/import tooling or the curated `lib/articles.ts` pattern; review the diff.
3. Run `npm run build` and `npm run lint` in an isolated dependency workspace when the shared Google Drive checkout cannot install packages.
4. Run browser smoke checks: archive count, representative article navigation, direct refresh, source-link behavior, search/filter behavior, and narrow mobile layout.
5. Publish the verified source through the Cloudflare Sites workflow only after the build and smoke checks pass.
6. Confirm the deployed version and live URL; record the commit/deployment identifier in the editorial log.

The weekly workflow is therefore: **intake → check → deduplicate → rights/source review → image → conditional PDF → import → build/lint → browser smoke test → deploy**.

## Weekly operating rule

For each new column, keep the intake JSON, source evidence, image provenance, PDF decision, and review result together. A missing URL or missing PDF is a documented follow-up item, not a reason to block unrelated verified records. Never publish a duplicate merely because it came from a different discovery channel.
